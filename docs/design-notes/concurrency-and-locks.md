# 并发与锁

## 问题

AstrBot 的插件 KV（`PluginKVStoreMixin`）只有 `get_kv_data` / `put_kv_data` /
`delete_kv_data` 三个方法，**没有事务、也没有 compare-and-swap**。任何
「读 → 判断 → 写回」的序列在并发下都会被击穿：两个请求读到同一份旧值，各自判断通过，
后写的覆盖先写的。

2026-09-06 的渗透实测确认了后果：带 IO 延迟的 KV 桩上，30 并发 / 配额 5 全部放行，
20 并发 / 冷却 10 秒全部绕过。所以在插件内用锁把「读-判-写」串起来，是唯一可用的
本地手段。

## 两把锁，边界不同

### 1. 限流闸门的实例锁（`services/gating.py`）

- `LimitGate` 持有 `asyncio.Lock`，串行化会话节流与每日计数的「读-判-写」。
- 保护范围是**同一个实例内**的并发请求。
- 热重载时前后两代实例各持一把锁，互不相识；两侧并发操作同一份 KV 时并不互保。
- 多进程部署完全不覆盖——框架侧没有分布式锁，这是已知限制。

### 2. 每日牌运的模块级写锁（`services/daily.py`）

- `_KV_LOCKS` 按事件循环存放 `asyncio.Lock`，同一个模块里的多个
  `DailyFortune` 实例共用，保护单键 `DailyRecord` 的「读-合并-写」。
- 模块级不是实例级，是为了让热重载后**同一代**的多个实例互保。
- 但热重载会重建模块字典，新旧两代各自一份锁——与实例锁一样，跨代不互保。
- 键用弱引用：未争用的锁不碰事件循环，循环回收后条目自动消失；因争用绑定过循环的
  条目，在取锁时按「循环已关闭」清理，避免测试里反复 `asyncio.run` 越积越多。

### 3. 同键生成去重（`services/singleflight.py`）

- `_SPIRIT_FLIGHT` / `_INTERP_FLIGHT` 是模块级的：同一代模块内多个实例共享同一笔
  生成，等待者被取消不会连带取消共享结果。
- 同样的边界：热重载后的新模块拿到的是新对象。

## 结论

- 锁只解决「同一进程、同一代模块、同一事件循环」内的并发。
- 多进程与热重载窗口不在保护范围内；那几秒里最坏是多算或少算一两次，不影响牌面
  正确性（每日牌抽牌本身是确定性纯函数）。
- 若将来要多进程部署，必须换成分布式锁或框架侧 CAS，别指望现有实现顺手兜住。

## 风险清单（2026-11-07 评估）

| 对象 | 机制 | 不覆盖的窗口 | 最坏后果 |
|---|---|---|---|
| `LimitGate` | 实例级 `asyncio.Lock` | 热重载重叠、多进程 | 会话节流与每日计数的「读-判-写」可能各读旧值后重复放行，计数偏差一次 |
| `DailyFortune` | 按事件循环的模块级锁，保护单键 `DailyRecord` 的读—合并—写 | 热重载重叠、多进程 | 两代实例读到同一份记录、各自写回不同字段；后写者可能覆盖先写者刚写入的 `interps` / `spirit_line` / `spirit_sign` / `spirit_persona` 或上下文指纹，导致部分 AI 解读与牌灵话丢失并重新生成 |
| `SingleFlight` | 模块级生成去重 | 热重载重叠、多进程 | 同一主题/牌灵被生成两次，白花一次 AI 调用 |
| `Renderer` | 实例级 `asyncio.Semaphore(2)` | —— | 只是渲染资源上限，与 KV 原子性无关；并发上限在跨代时也只是各自算各自的 |
| `AiInterpreter` | 按事件循环 + Provider 的信号量 | —— | 只是 Provider 并发上限，不是 KV 锁；不应为「锁生命周期统一」迁到存储层 |

判断：

- 这不是单实例正常运行下的确定性缺陷，只在热重载重叠或多实例共享同一份 KV 时出现。
- 每日牌面由 `_daily_pick` 的确定性种子决定，不受上述窗口影响；风险集中在**缓存字段**与**限流计数**。
- 缓存字段被覆盖的后果是可恢复的：下一次读取按未命中处理，重新生成解读或牌灵话，
  代价是一次 AI 调用，不会给出错误牌面。

评估问题与结论：

1. **热重载重叠是否可观测？** 只在面板热重载 / 重装插件后的数秒窗口内可能发生；正常单实例运行不触发。本轮没有在真实面板上复现（未验证，按代码路径推断）。
2. **最坏后果是否仅为限流偏差 + 缓存字段重新生成？** 是。牌面不变，索引最多少列一个用户，解读与牌灵话可重新生成。
3. **是否有多进程需求？** 当前部署是单进程 AstrBot，没有；将来要多进程时，进程内锁完全无效，需另立分布式锁 / CAS 任务，不在这份设计内解决。

明确不做：

- 不把 `Renderer` 与 `AiInterpreter` 的信号量迁移到存储层——它们控制的是 CPU/内存与上游 Provider 压力，不是 KV 原子性。
- 不为热重载窗口引入新锁或代际协调机制。
- 不引入通用锁框架；多进程方案另立任务。
